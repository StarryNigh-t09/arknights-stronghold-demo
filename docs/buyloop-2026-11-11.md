# 休整期买卡循环（2026-11-11 重写）

## 依据
用户 m00211 / m00267 的原话规则：

1. 先判断要不要升级商店。
2. 钱够就买想要的卡（点卡片任意位置，同一点连点两下＝选中+购买）。
3. 没有想要的卡就刷新，1 块钱一次，没有次数上限。
4. 钱不够买想要的卡、而店里正好有 → 冻结并停手。
5. 店里没有想要的卡 → 继续刷新。
6. 刷到没钱 → 不冻结，等下一回合自动刷新。
7. 冻结前先把钱花掉（买得起装备/对子就买）——m00267 确认。
8. 装备不占「剩余可放置角色」；整备区上限 10 张、装备上限 5 个（m00211/m00214）。
9. 整备区满了就卖掉没用的干员 —— **这条是决策，暂未实现**，目前满了只允许升级/买装备，否则停手。
10. 只有买卡时商店才展开，其余操作（装装备、量整备区、卖卡、拖人）一律折叠态（m00233）。

## 实现结构
- 纯决策：`world/lib/restplan.js` → `planRestStep(ctx)` 返回下一动作（upgrade / buy / refresh / freeze / stop）。
  顺序：升级 → 买想要的干员 → 买得起的装备 → 有想要的但买不起（钱 0 就停、有钱就冻结）→
  没有想要的：免费刷新 → 花钱刷新 → 兜底买最便宜的 → 停。
- 只做点击和核对：`world/lib/drive.js` 里的 `restBuyTurn()`，每一步都验证成交后才记账。

## 这次修掉的坑
1. **刷新点了 36 下一动不动**。三个原因叠在一起：
   - `hasFreeRefresh()` 只会判「徽章在不在」，判不出「还剩几次」，徽章挂 x4 但次数用完仍报免费；
   - 免费刷新只比较钱，钱本来就不变，所以每次都算「成功」；
   - 真正的失败是按钮变灰（店已冻结 / 合成后的特殊店），点它没有任何反应。
   现在：免费次数用 OCR 读徽章上的数字（FREEX4 → 4）；刷新成功后必须看到店里卡面变了（内容指纹）；
   点之前先看按钮颜色，灰了直接收工。
2. **清单永远是空的**：调用方传的是字符串 `'auto'`，不是数组，`wantList.length` 恒为 0 → 买卡阶段把钱全刷光。
3. **甲板满闸门量纲错**：`deck.length >= slotsLeft` 把「剩余可放置角色」当成整备区上限，实际那是部署位；
   真正上限是 10 张（BENCH_CAP）。
4. **账本只增不减**：买卡 +1，上场/卖卡/被清空都不减，越跑越「满」。
5. **买卡不校验**：点了就 push，没成交也记。现在只用「钱了变少」或「卡从店里消失」判成交。
6. 旧决策块（adviseRest 对子覆盖/清单缺口/诊断行）残留 51 行，已删。

## 第二轮修复（2026-11-11 11:00–11:50）

### 1. 钱数读不出来 / 一直不变 —— 根因与修法
- 现象：买卡循环每步都报「钱数没读出变化」，预算判断失真（round3 连买 5 件 1 块装备，钱数恒为 1）。
- 根因：金币字体里的「1」被 OCR 认成竖线。折叠态钱 14 读成 `|4` → `4`；展开态钱 1 读成 `|` → 没有数字 → None。旧 `read_money` 只扫一条固定窄矩形，同时没做字形归一。
- 修法（world/sidecar/ocr.py：`_norm_digits` + 重写 `read_money`）：扫描右侧竖带 (1700,690)-(1920,960)，把 |/l/I/! 归一成 1、O/o/Q 归一成 0，只收纯 1~2 位数字候选，**取最靠下的那个**（金币徽章永远在冻结/刷新按钮下面）。
- 验收：四张基准图全对 —— `_live4.png` 7、`_shop_now.png` 14（旧读法 4）、`_now.png` 2、`_buy7.png` 3；真机 `_m1.mjs` 实读 money=7 与画面一致。

### 2. 商店等级还会误降
- 现象：日志两次出现「商店等级按 OCR 校正：Lv4 → Lv3」「Lv2 → Lv1」。
- 根因：`autoRest` 里有两处校正点，第一处（折叠态那次）直接赋值，允许往下改。折叠态 LEVEL 面板被甲板压着，读出来偏低。
- 修法（world/lib/drive.js）：第一处也改成「只在 `shopIsOpen(st)` 为真、且新等级 **大于** 当前等级时才接受」，与第二处一致；注释写明两次误降的实测时间。

### 3. `bought` 记录是 [null,null]
- 根因：`autoRun` 兜底从 steps 里切字符串，新循环的行格式是「买卡 → buy：…」（全角冒号），旧的 `split('→ buy ')` 切不出来。
- 修法：优先用 `rest.bought`（成交时 push 的真实卡名），兜底解析改成 `split('→ buy')[1].replace(/^[：:]\s*/, '')`。

### 4. 实测（fresh2 局，补丁前半段代码跑 3 回合）
- round1 moneyLeft 4 / round2 moneyLeft 5，钱数在回合边界读对了。
- 买卡段日志正常出现「升级 → 买装备 → 刷新 → 刷新按钮灰了停手」，说明免费刷新计数、按钮灰度、停手判据都在工作。
- 装备买满 5 件后游戏弹「装备已满，无法继续购买装备」，循环仍尝试买装备 —— 靠 `equipCount<5` 拦，但在同一回合里靠的是自己数的件数，游戏端拦截时会白点一次，已记成已知瑕疵。

### 5. 未验证 / 已知瑕疵
- 等级只升不降这条补丁**还没在真机上跑到**（本次 3 回合跑的是补丁前的进程）。
- 装备满后的「白点一次」没去掉。

## 第八轮（20:35–20:50）：拖拽卡死的根因找到了

现象（trace-11-09-05 第 8 回合 19:24、trace-12-19-53 第 6 回合 20:37 各一次）：
画面停在一名**已经在场上的干员**被按住 —— 左侧弹干员面板（生命、出售 +1、攻击范围菱形）、
右侧「剩余可放置角色：0」、脚下一片黑色「不可放置」标记，之后「准备就绪」怎么点都没反应，整局到此为止。

根因：**定朝向那一步滑得太远。**
`world/lib/run.js` 的 `FACING_VEC = { right: [600, 0], ... }`，放完干员再长按格心往右滑 600px。
600px 在游戏里不是「转个朝向」，而是「把干员挪到别处」；滑到非法格 → 游戏停在等你落位的移动模式，
手指虽然松了，状态没退出来。所以每次布阵收尾都可能把一个人挂在手上。

修法（两条一起）：
1. `FACING_VEC` 从 600px 缩到 **70px**（只够触发朝向判定），定朝向的按压从 50ms 加到 120ms。
2. 新增 `world/lib/run.js` 的 `export async function deselectUnit()` —— 点一下战场右上角空地 (1700,250) 取消选中；
   `deployFromDeck` 收尾必调一次。实测手动点 (1700,250) 能把卡死状态解开（截图 `_now11c.png`）。

验证：改完后接着跑同一局，第 6→7→8 回合正常推进（第 6 回合 124s 一滴血没掉），
第 7 回合掉 10 血（场上 8 人全是 1 阶、名额 0 换不了人，属决策层）。

顺带记一条数据：`occupiedPx` 会把**失败过的格**也记进去，跨回合累积，最终会「候选格剔掉已占的 19 个 → 剩 0 个」，
到那时布阵直接放弃（trace-12-19-53 第 6 回合就是这样）。下一步要么只记成功格，要么失败格带回合过期。
